# 2024 S2：HashingBox 黑盒测试

正式作答文件：**Q2Test.java**。原题要求见本目录README或测试文件注释。

正式答案保留13个原实现的参数化框架，新增5个 `@Test(timeout=1000)` 方法：所有合法size、名字与ASCII边界、所有材质/形状、负size异常、size>31异常。此题不要求最少测试数；循环中的每个输入也是一次实际检查。

### expected 怎么算

只看 README：最大的≤size的质数（size=1特殊取2）；名字前6个**位置**里只加英文字母ASCII；再乘sizeHash，加**完整名字长度**，最后加材质值×形状值。

例如 `SILVER,3,SQUARE,"Comp2100"`：`(67+111+109+112)*3+8+925*4=4905`。`AZaz` 的expected是4826；`AbCdEf`是5209。不是先把所有非字母删除，再取前6个字母。

### 辅助类怎么用

`ExpectedCalculator.java` 是按规范写的独立计算器。main逐个显示字符编码并打印hash；只需修改开头的name、size、material、shape四个变量。计算用质数数组、普通for循环和if，公式分步写明。它**不会调用某个HashingBox来生成正式expected**。原来的 `asc.java` 保留不变。

`LocalValidation.java` 先用独立规范参考实现验证测试本身，再运行13个原实现。本地结果：HashingBox10通过当前测试，其他12个实现被检出错误；原JUnit运行65项，21项失败是预期的缺陷检测结果，不能把它们改成通过。

### 必须知道的原题冲突：size=0

README写范围1～31，因此0按文字规范应抛 `ComponentOutOfRangeException`。但基类用 `<0` 判断，13个原实现实际都没有对0抛出规定异常。这与“有1～3个正确实现”的说法不一致。

本答案明确避开争议值0，测试-1和32，并由LocalValidation单独核对0的实际行为；没有把0说成规范允许，也没有擅自修复被测实现。若考试明确以1～31为严格评分依据，应增加独立的size=0异常测试；在当前这套原文件中，它会令所有实现失败。当前分类仅针对已测、无争议的输入，不能据此宣称HashingBox10完全符合README。

## 直接运行

在本题文件夹打开终端：

```bash
python3 ../run_all.py --only 02 --helpers
```

也可以在已配置Java依赖的IDE中打开 `ExpectedCalculator.java`，点击main旁的Run。修改main中的参数、普通变量或数组，重跑获取expected，再把**确定的数值/布尔值/异常类型**写回正式测试。辅助类不属于考试提交文件，不要直接多交；正式答案不依赖辅助类计算expected。

统一脚本把编译产物放在临时目录，不会把.class或XML运行输出混进题目文件夹。若直接编译，请保留本题原package结构和JUnit版本。
